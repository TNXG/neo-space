# Neo-Space API 设计

## 使用目标

指导未来如何设计 API，而不是复述一次检查结果。适用于新端点、现有端点扩展、API 客户端设计，以及新管理面板的数据契约设计。

**从业务能力和权限出发，先确定契约，再编写实现与界面。** 优先级：正确性 → 端到端一致性 → 长期可维护性 → 实现便利。

以下规范是设计目标，不代表当前每个接口都已满足。历史差异另记在根目录 `API-AUDIT.md`，不得把差异自动升级为新约定。

## 1. 先确定能力与边界

动手前回答：

- 谁需要什么能力？匿名访客、普通读者、资源作者，还是 owner？
- 是资源读取、资源变更，还是独立的业务动作？
- 哪个实体拥有这些数据？哪些字段属于公开数据、管理数据或敏感数据？
- 已有端点能否表达需求？如果能，应复用，不建立第二套同义接口。
- 本轮是否真的需要后端新增能力，还是只缺前端封装？

列出能力矩阵：

| 业务能力 | 资源 | 使用者 | 允许动作 | 现有契约 | 本次新增/调整 |
| --- | --- | --- | --- | --- | --- |

先查 `apps/backend/src/app.rs` 的挂载与 `routes/` 注册，再读 handler/service/model；不能只依赖旧 UI、TypeScript 类型或 OpenAPI。

对现有契约不一致，默认先改前端类型 → adapter/API 封装 → 组件。不要为了界面方便修改后端字段或扩大权限。确需变更后端契约时，先明确业务理由、授权、所有调用方与迁移范围。

## 2. 资源路径与 HTTP 方法保持可预测

- 常规 REST 接口沿用 `/api` 前缀；健康检查、WebSocket、静态资源分别遵循现有挂载。
- 使用清晰的资源集合与详情路径，复用项目已有命名，不新建同义单复数别名。
- GET 表达读取；POST 表达创建或明确业务动作；PUT 表达整体替换；PATCH 表达部分更新；DELETE 表达删除。
- 恢复、发布、解锁等无法自然表达为资源 CRUD 的动作，应有明确路径、请求和权限，不伪装成 GET。
- 列表筛选放 query，创建/变更数据放 JSON body，资源定位放 path；不要把秘密凭据放 URL。
- 明确 URI 编码、允许值、默认值、空值语义及错误行为；客户端不能直接拼接未经编码的用户输入。
- 避免动态详情路径吞掉静态入口；核对完整挂载路径而非局部 `.route()` 字符串。
- 不为“可能以后需要”预建路由、兼容层或通用抽象。

既有端点的方法或行为可能与理想语义不同。未经授权不要悄悄改变它；明确记录差异，再决定是否迁移全部消费者。

## 3. 身份标识统一为 `_id`

- 后端业务实体的公开主键为 `_id: string`，ObjectId 序列化为文本。
- 请求模型、响应模型和业务组件统一使用 `_id`；禁止 `id || _id` 双轨兜底。
- `{id}`、`?id=` 可以是路由参数名，但承载的值仍是实体 `_id`，不因此新增响应字段 `id`。
- slug、nid、OAuth provider ID 与实体主键是不同标识，应明确各自查询入口与类型。
- 组件可派生 `key` 供 UI 库使用，但不得把视图别名扩散到 API/存储层。
- 搜索索引、第三方服务或历史存储字段通过边界 DTO/adapter 映射，不向所有消费者传播存储细节。

## 4. 先定义请求、响应与 DTO

每个端点在实现前确定 path/query/body DTO 与成功/错误响应，列明必填性、可空性、枚举、默认值和字段可见性。

目标响应契约：

```ts
type ApiResponse<T> = {
  code: number;
  status: "success" | "failed";
  message: string;
  data: T | null;
};

type PaginatedData<T> = {
  items: T[];
  pagination: {
    total: number;
    current_page: number;
    total_page: number;
    size: number;
    has_next_page: boolean;
    has_prev_page: boolean;
  };
};
```

- 错误响应也维持统一包装，`data` 为 `null`；HTTP 状态与 `code` 保持一致。
- `message` 用于人类可读说明，token、分页、标识等业务数据放入有类型的 `data`，不要藏在消息文本。
- 列表请求沿用 `page`、`size`，明确边界、排序与筛选；返回固定的 `items + pagination`。没有需求不要引入第二套 cursor/offset 分页。
- 成功后返回更新后的实体、URL 或 `null`，应按消费者真实需要选择并写进契约，不盲目返回完整数据库文档。
- `null`、缺省字段、空数组、空字符串含义不同；TypeScript 必须忠实表达。
- Rust `Option<T>` 配合序列化属性确定实际 JSON 形状；不得一概写成 TS 可选字段。
- 任意 JSON 使用具体结构或 `unknown`，不得写成 `string`，也不得使用 `any`。
- 仅在明确的 adapter 边界进行字段转换；不使用全局隐式 camelCase 转换隐藏契约问题。
- DTO 是边界。公开 DTO、管理 DTO 与 Mongo 文档可共享必要类型，但不能直接复用敏感存储模型输出。

## 5. 将权限作为设计输入

为每个动作分别填写权限表，不从“已登录”推导“可管理”：

| 动作 | 匿名 | 普通读者 | 作者本人 | owner | 返回字段范围 |
| --- | --- | --- | --- | --- | --- |

- 新端点默认按最小权限设计，服务器执行授权；UI 隐藏按钮不能代替授权。
- 逐个区分查看、创建、编辑、删除、审核、批量操作。作者可编辑不自动意味着可删除。
- 公共读取与管理读取分开定义。公共列表不能假装包含未发布、隐藏或待审核数据。
- 明确使用 Bearer、HttpOnly Cookie 或服务端转发的哪种身份链路；不要混合出不可预测的优先级。
- Server Action/服务器 fetch 不会自动带上浏览器凭据，必须显式转发所需凭据。
- 跨源 Cookie 需要共同设计 `credentials`、CORS 和 Cookie 属性；敏感 token 不进入客户端 bundle、URL、日志。
- 401 表示缺失/无效身份，403 表示权限不足；客户端分别处理。
- 公开数据最小化：邮箱、第三方凭据、管理字段不因模型复用而泄露。

## 6. 分离读取、变更与前端调用边界

在 `apps/web` 中设计调用方式时：

- 首屏读取由 Server Component 经 `@/lib/api-client` 请求后端；`page.tsx` 只编排，不堆积业务逻辑。
- 实时、轮询、无限滚动等读取使用 SWR/TanStack Query；禁止 Server Action 做纯读取，禁止 `useEffect + fetch` 手写数据加载。
- 变更默认由 Server Action 代理，成功后按依赖 `revalidatePath`/`revalidateTag`；即时交互例外遵循项目既有规范。
- 请求泛型包含 `ApiResponse<T>`，先判断成功/失败，再处理可空 `data`；不混淆 HTTP/axios 外层响应与业务数据。
- 公共站与管理面板复用稳定的传输/鉴权机制，但分别提供准确的业务 DTO 和方法；不把公共客户端误当成完整管理客户端。
- 新管理面板在 `apps/web` 的 App Router 路由组内实现时，仍须保持服务器/客户端边界，不跨 app 导入旧 Vue 实现。
- 在添加封装前查已有模块；搜索、聚合、第三方服务与流式请求可能已有专门入口。

## 7. 后端职责分层与写后一致性

- `routes/` 只做路由和中间件挂载；`handlers/` 解析参数、调用 service、包装响应。
- Mongo 查询、权限相关业务规则、缓存与事件在合适的 service 层实现，避免 handler 直接堆积查询。
- 使用 `AppError` 与项目提取器统一错误；新增 handler 补充 Utoipa 描述并注册到文档入口。
- 按项目要求控制 Rust 模块长度，按职责拆分而非建立“万能服务”。
- 读取使用项目现有缓存策略；鉴权相关数据不得进入无身份区分的公共共享缓存。
- 写入成功包括相关 Moka key 失效、`<entity>.<action>` 事件广播，以及必要的前端按需 revalidation。
- 明确一次业务操作的成功边界；不要以数据写入成功掩盖必要的派生状态未同步。
- 不为普通 CRUD 默认附加重试、幂等键、遥测、队列或复杂事务。确有业务风险时再设计对应机制与失败语义。

## 8. 错误与演进必须显式

- 错误保留 HTTP 状态和可理解的消息，区分参数、身份、权限、资源不存在、业务冲突、依赖故障与内部错误。
- 状态码以实际提取器与 `AppError` 映射为准，不能照抄框架默认值。
- 不用空数组、假实体、假成功或 catch 后默认值掩盖接口失败。
- 用户交互明确展示加载、成功、失败，日志不泄露秘密或个人数据。
- 新需求优先向后端真实能力对齐；新增字段/方法时检查全部调用方，不保留长期别名和废弃 shim。
- 对现有契约做清晰切换，迁移相关类型、封装、组件、文档及有效测试；未经授权不扩大改动范围。

## 9. 设计完成的交付物

新增或调整 API 时，先输出下面的简短契约卡，再实现：

```text
能力与资源：
调用者及权限：
Method + 完整路径：
Path / Query / Body：
成功 HTTP 状态与 ApiResponse.data：
错误条件、HTTP 状态与错误体：
分页、排序、过滤（若适用）：
鉴权传递与字段可见性：
缓存、写后失效、事件与 revalidation：
现有调用方与迁移范围：
实现文件及 OpenAPI 注册：
实际验证场景与外部依赖：
```

不适用项写明不适用，不添加没有业务需要的设计。

## 10. 验收与证据

- 从实际调用入口验证成功、参数边界、无权限与必要的失败路径；写后再读以确认状态和缓存。
- 测试应覆盖消费者可见的行为、权限、边界、错误和状态转换，不测试源码字面值、机械转发或 mock 回声。
- typecheck 与单元测试不能代替运行真实接口或实际页面。
- 先检查验证操作是否会写库、生成内容或调用付费服务；GET 不必然无副作用。
- 缺少会话、后端离线或外部依赖不可用时，明确未验证项，不能宣称“完整可用”。
- 分清源码确认、源码推导、运行时实测与未验证。
- 只检查的任务不修复、不建面板、不启动可能写库的服务；执行范围以用户当前授权为准。

最终检查：资源与方法明确，`_id` 一致，请求与响应类型真实，权限及可见性明确，缓存正确失效，全部消费者完成迁移，文档与实测证据齐全。
